# Minecraft API・回帰バグ調査

## タスク種別の判断

- 症状に「以前のバージョン/移植前は動いていた」が含まれる → **ワークフロー B (回帰調査)**
- それ以外 (新機能の実装前調査、移植と無関係なバグの API 理解) → **ワークフロー A (API 調査)**
- 迷ったら: バージョン移植の diff が関与しうるなら B。B は A の手法を包含する

## 調査の原則 (共通)

1. **バニラ API の挙動を記憶で断定しない。** バージョン間で内部実装が変わるため、「このメソッドはこう動くはず」という知識が一番信用できない。必ず jar から確認する。
2. **既存コードのパターンを先に見る。** プロジェクト内の類似実装・既存の API 使用箇所が最短の一次情報。
3. **登録側と消費側の両端を突き合わせる。** mod が「どのキー/ID/パスで何を登録するか」と、バニラエンジンが「どのキーで要求するか」を別々に確認し、不一致を探す。片側だけ読んで正しく見えても、もう片側の要求形式が変わっていれば壊れる。
4. **クロスプラットフォーム。** Fabric/Forge の差異に注意し、Architectury の抽象があればそちらを優先して提案する。

## jar-search.sh (共通ツール)

```bash
S=.claude/scripts/jar-search.sh
$S doctor    # 最初に実行: ソース jar / javap の状態を診断し、使うべき経路を案内する
```

ソース jar があるとき (`find`/`grep`/`read`):

```bash
$S find <Class>                       # クラスの場所を検索 (全 jar 横断、現 MC バージョン)
$S find <Class> --dir minecraftMaven  # Minecraft 本体 jar のみに絞り込み
$S grep <jar-pattern> <pattern> [N]   # 特定 jar 内をキーワード grep (jar は部分一致)
$S read <jar-pattern> <path/to/Class.java>  # ソースを読む
$S list [filter]                      # 利用可能なソース jar 一覧
```

ソース jar が無いとき (javap 系、ソース不要・即時):

```bash
$S sig <Class>                      # メンバのシグネチャ一覧 (クラス構造の把握)
$S bytecode <Class> <method>        # 特定メソッドのバイトコード (挙動・呼び出し先の確認)
$S bytecode <Class> "static"        # static イニシャライザ (定数・FINDER 等の初期化値)
$S apidiff <Class> <旧バージョン>   # 旧→新のシグネチャ diff (何が変わったかの一覧)
```

逆参照 (どちらのモードでも使用可):

```bash
$S callers <Class>                  # クラスを参照しているクラスの一覧
$S callers <Class> <method>         # メソッドの呼び出し元 (呼び出し箇所のバイトコード行付き)
```

共通オプション: `--all` でバージョンフィルタ解除 (命名規則の変動でヒットしない場合)。

バイトコードで確認できること (例):
- `ldc #NN // String sounds` — メソッドが使う文字列定数 (prefix/拡張子の再付与などが見える)
- `invokevirtual #NN // Method ...` — 実際の呼び出し先 (どの経路で消費されるか)

## ワークフロー A: API 調査

1. **既存コードの確認**: プロジェクト内の類似実装・既存の API 使用箇所を grep する。
2. **API クラスの追跡**: jar-search.sh で対象クラスの構造 (`sig`)・挙動 (`read` または `bytecode`)・継承関係を確認する。
3. **消費経路の確認**: override/登録するものは `callers` でバニラ側の呼び出し元を特定し、いつ・どこから呼ばれるかを把握する。
4. **クロスプラットフォーム**: Fabric/Forge で差異がないか、Architectury 抽象があるかを確認する。

**報告形式 A** (シグネチャ以外のコード転載禁止 — コードブロックでもインラインコードでも):
- **Summary**: 調査質問への簡潔な回答
- **Key Classes/Interfaces**: パッケージ付きの関連クラス
- **API Details**: メソッドシグネチャ・フィールドとその役割 (自分の言葉で)
- **Usage Pattern**: API の使い方 (自然言語で記述、コードを写さない)
- **Cross-Platform Notes**: Fabric/Forge の差異
- **Caveats**: スレッド・サイド制約・バージョン注意点

## ワークフロー B: 回帰調査

移植後の回帰バグの root cause は、ほぼ必ず **「移植時に mod 側で変えたもの」と「バニラ側で変わった挙動」の交点**にある。コードを眺めて推測を積み上げる前に、この 2 つの一次情報を取ること。

**「何は動いているか」が最大のヒント。** 「デフォルト音は鳴るがサウンドパックの音は鳴らない」のような部分的な生存は、生きている経路と死んでいる経路の分岐点を教えてくれる。症状を「壊れた」で止めず、動く/動かないの境界を先に言語化する。

### B-1. 症状の整理と経路の特定

- `TODO.md`、`docs/research/`、`docs/log/` を読み、症状・再現条件・過去の調査記録を把握する。
- 関連コードを特定する (`find`/`grep`、例: `find . -iname "*sound*"`)。
- 処理の流れを追う: mod 側の登録処理 → バニラ側の消費処理。

### B-2. 移植 diff を疑う

移植ブランチと旧バージョンブランチの diff は「mod 側で何を変えたか」の一次情報。

```bash
git diff <旧バージョンブランチ>..<現ブランチ> -- <関連ファイル>
git log --oneline -S "<消えた/変わったシンボル>" -- <ファイル>   # いつ変わったかの特定
```

特に見るべきパターン:
- **匿名クラス・override・条件分岐の削除**: 機械的な API 追従のついでに、挙動を持っていた override が一緒に消えることがある (頻出の回帰源)
- **`new X(...)` の引数型変更**: 型が変わった引数に渡している値の「形式」(prefix/suffix/名前空間の有無) が新 API の想定と合っているか
- **描画・イベントの順序変更**: `super.render()` の呼び出し位置、イベント登録タイミングなど、順序に意味があるコードの並び替え

### B-3. バニラ API の挙動を jar で確認

jar-search.sh で登録側・消費側の両方を裏取りする。**消費側の経路も必ず確認する** — mod が override/登録したものを、バニラのどのメソッドが実際に呼ぶのかを `callers` と `bytecode` で追う。呼ばれない場所をいくら直しても回帰は直らない。旧→新で何が変わったかは `apidiff` で一覧できる。

### B-4. 仮説の照合

root cause 候補が見つかったら、以下の 3 点すべてを説明できるか確認する。1 つでも説明できなければ、それは root cause ではないか、複数原因の一部でしかない。

- **なぜ旧バージョンでは動いていたか** (旧コード/旧 API の何が守っていたか)
- **なぜ今壊れたか** (何が変わって防御が外れたか)
- **なぜこの症状か** (部分的に動く場合、その境界と仮説が一致するか)

**報告形式 B**:
- **Root cause**: 1〜2 文で断定形。「〜の疑い」で終わらせない (確定できない場合は何を確認すれば確定するかを添える)
- **旧バージョンで動いていた理由**: 移植で失われた防御・前提
- **症状との整合**: 部分的に動く理由の説明
- **最小修正方針**: 変更箇所と方法。代替案がある場合は却下理由も
- **根拠**: file:line、コミット hash、javap/diff の出力の要点

## してはいけないこと

- **実装コードの生成・修正の実装・コミット** — 調査専任。修正方針の提案まで
- **gradle ビルド・テストの実行** — 時間がかかり調査には不要 (`doctor` が案内する genSources も提案に留め、実行は呼び出し元に委ねる)
- **記憶にあるバニラ API 仕様での断定** — 必ず jar で裏取りする
- **診断のための対象コード書き換え** — read-only で調査する
- **デコンパイルソース等の転載** — シグネチャ以外の実コードを出力しない (コードブロックでもインラインコードでも。対象プロジェクトのコードも同様)
